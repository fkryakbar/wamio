## Development commands

### App lifecycle (Wails)
- Install Wails CLI (if needed): `go install github.com/wailsapp/wails/v2/cmd/wails@latest`
- Live development (Go backend + Vite frontend): `wails dev`
- Production desktop build: `wails build`

### Frontend (run inside `frontend/`)
- Install dependencies: `npm install`
- Dev server only: `npm run dev`
- Build frontend assets: `npm run build`
- Preview built frontend bundle: `npm run preview`

### Backend tests (run from repository root)
- Run all Go tests: `go test ./...`
- Run a single package: `go test ./internal/whatsapp`
- Run a single test: `go test ./internal/whatsapp -run TestName`

## Architecture overview

This is a Wails desktop app that embeds a React + TypeScript frontend and binds Go services directly into the UI runtime.

### Runtime composition
- `main.go` bootstraps Wails, embeds `frontend/dist`, and binds `App` plus `WhatsAppService` into the frontend bridge.
- `app.go` handles lifecycle (`startup`/`shutdown`) and injects Wails context into `WhatsAppService`.

### Backend domain model
- `internal/whatsapp/service.go` is the core orchestration layer:
  - Manages WhatsApp connectivity via `whatsmeow`.
  - Owns connection/session state and emits Wails runtime events (e.g. connection updates, chat updates, incoming messages).
  - Maintains in-memory chat/message caches for fast UI reads.
  - Coordinates persistence and media caching.
- `internal/whatsapp/chat.go` and `internal/whatsapp/media.go` contain chat/media-specific behavior used by the service.
- `internal/whatsapp/types.go` defines shared backend DTOs/events consumed by the frontend bridge.

### Persistence strategy
- `internal/store/database.go` initializes per-account SQLite databases under the user config directory (`.../Wamio/accounts/<accountID>/session.db`) with WAL mode.
- `Database` wraps whatsmeow SQL store migration/session storage and exposes `sql.DB` for shared use.
- `internal/store/chatstore.go` persists chat/message history beyond in-memory runtime caches.

### Frontend state + event flow
- `frontend/src/App.tsx` is the integration point for backend events:
  - Subscribes to Wails runtime events (`EventsOn`) such as `wa:connection`, `wa:chats-sync`, `wa:chat-update`, `wa:message`, `wa:notification`.
  - Loads initial chats through generated Wails bindings in `frontend/wailsjs/go/whatsapp/WhatsAppService`.
  - Switches between login and chat UI based on auth connection state.
- Zustand stores are the client-side state backbone:
  - `frontend/src/stores/authStore.ts` for connection/auth status.
  - `frontend/src/stores/chatStore.ts` for chat list, active thread, message cache, sync/search/read state.
- UI components/pages consume store state and backend-bound methods; backend is event-driven while frontend keeps normalized local state for rendering.

### Generated bridge artifacts
- `frontend/wailsjs/` is generated by Wails and contains typed Go method bindings and runtime helpers used by the frontend. Treat as generated output unless regeneration is intended.
